## 2. 逐项评审

### 2.1 认证与会话（`auth.py` / `sessions.py`）✅
- 服务端 session 方案正确：`uuid4().hex` 为 sid，会话 JSON 落 `data/sessions/`，Cookie 只含随机 id，`HttpOnly; SameSite=Lax; Max-Age=7d`；登出删除服务端文件，reset 清空 sessions 目录即"退出登录"成立。
- `get_current_user` 每次请求实时查库 ⇒ banned 会话下一次请求即 403（决策 dec-0f895a1ddd678090），测试已覆盖。
- 判定顺序 401（无/失效会话）> 403（banned）落实正确。
- **【P3 观察项】** Cookie 未设 `Secure`——本地 HTTP 验收没问题（需求文档已明确 TLS 非验收项）；若部署到公网需加。会话 TTL 7 天为硬编码常量，无"记住我"配置，属可接受简化。

### 2.2 用户注册/详情/列表（`users.py` + `services/users.py`）✅
- 注册校验链路完整：pydantic `min/max_length` → 422→400 全局处理器 → service 层 strip 后防御校验 → 唯一性 400；密码 bcrypt 落盘，响应不含 password。
- `user_id` 自增逻辑（admin="0"，首个普通用户="1"）与 api.md 注册示例对齐。
- 详情权限：本人/管理员可见，普通用户查他人 403（不泄露存在性），管理员查不存在 404；响应含 username/role，符合需求文档 §5 Step4。
- 列表分页语义与 submissions 一致（page 有 page_size 空 → 400；page_size 有 page 空 → 第 1 页；全空 → 全量；<1 → 400），响应 `{total, users:[...]}`，均正确。
- **【P2 建议】注册/登录/创建管理员的响应 data 字段建议逐字段对照官方 api.md**：本仓库未收录 api.md 原文，注册返回了 `user_id/username/join_time/role/submit_count/resolve_count` 六字段，若自动评测做严格全等比较，多字段可能有风险。通常多字段不扣分，但建议在 D3 前人工核一遍官方文档示例。

### 2.3 权限变更与管理员创建（`change_role` / `POST /api/users/admin`）✅
- role 白名单校验 400 → 404 → 403 的优先级正确；权限操作日志（operator/target/old/new/time）落 `data/logs/role_changes/`，与 Step5 access 审计区分清晰。
- 创建管理员复用 register + change_role，重名 400、非管理员 403 已测。
- **【P3 观察项】** 管理员可以把自己改 banned/user，导致系统瞬间失去可用管理员（需 reset 恢复）。api.md 未禁止，可不改；建议至少在文档记录该语义，避免验收演示时误操作。
- **【P3 观察项】** `get_by_user_id`/`next_user_id` 为 O(n) 全目录扫描；当前数据量可接受，D3 接入题目后如需频繁按 user_id 查询，可加内存索引。
