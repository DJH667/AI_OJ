## 2. 逐项评审

### 2.1 统一响应与异常处理 ✅（建议 P1/P3）
- `success()` 与 `ApiError` 输出结构符合 `{code, msg, data}`，且 HTTP 状态码与 `code` 一致；422→400 处理器已就位。
- 判定优先级 401>403>400>429>409>404>500 的注释正确，且明确为"业务层落实"，分层清晰。
- **【P1 建议】缺少兜底 Exception 处理器**：未预期异常目前会以 Starlette 默认的纯文本 500 返回，破坏"所有接口 JSON 必须含 code"的全局契约。建议 D2 补 `@app.exception_handler(Exception)`，统一返回 `{"code":500,"msg":"internal server error","data":null}`，并保证不泄露堆栈/路径。
- **【P3 建议】HTTPException 的 msg 直接用 `str(exc.detail)`**，会出现英文 "Not Found"/"Method Not Allowed"。后续业务 404/405 应统一为契约化中文 msg 表，避免前端提示不一致。

### 2.2 JSON 存储层 ✅（建议 P2/P3）
- key 经 `quote(safe="")` 编码防路径注入，特殊字符 roundtrip 有测试覆盖，设计正确。
- `clear_all()` 保留目录结构、reset 语义与需求文档一致。
- **【P2 建议】`load_json`/`iter_all` 静默吞掉 `JSONDecodeError`**：损坏文件与"不存在"无法区分，`ensure_admin()` 会把损坏的 admin 记录当缺失而覆盖重写。建议至少记日志，或返回可区分的结果（如 `(ok, data)`）。
- **【P3 建议】`save_json` 直接覆盖写，无原子性**（先写临时文件再 rename）。当前数据量小、单用户串行可接受，建议列入备忘，评测/重置并发场景再评估。
